# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Duskline is a client-side web app for landscape lighting contractors: design a lighting layout on top of a customer's photo (drag-and-place fixtures, aim beams, draw wire runs and LED strips) and generate a customer quote / PDF from the same data. There is no build system and no package manager — the UI is one file, `index.html` (renamed from `duskline-lighting-designer_21.html` for Phase 4 — static hosts serve `index.html` at the root URL with zero config; ~3300 lines: inline `<style>`, inline `<script>`, no external JS files except CDN-loaded SheetJS and `@supabase/supabase-js`). It has a real Supabase backend for auth, app data, and photo/logo storage now (see "Auth & backend" below) — `localStorage` is no longer used for anything except small UI prefs (theme).

This directory **is now a git repository** (initialized as part of the backend migration below), but has no `package.json`, no test suite, and no linter configured. Treat every change as a direct edit to the one HTML file.

The two markdown files here (`duskline-going-live-roadmap.md`, `duskline-subscription-launch-plan.md`) are advisory planning documents (not app docs), written before any backend existed, describing a phased plan to move this from a local-only file to a hosted multi-user product on Supabase with Stripe billing eventually. **Phases 1–4 of that plan are now implemented**: real accounts, projects/fixtures/company data in Postgres, photos/logo in real file storage, and the app is live at `https://duskline.ca` (see "Auth & backend (Supabase)" below, and the migration-progress checklist for deploy details). Billing (Phase 5) and ongoing hardening (Phase 6) are still not implemented.

Other open items worth resolving before real customers sign up (not blocking further dev work):
- **Email confirmation** is currently OFF for this Supabase project (test signups return an active session immediately, no email-verification step) — fine for development, but decide deliberately before production.

## Running / testing changes

There's no dev server or build step. To check a change:
1. Open `index.html` directly in a browser (double-click, or serve the folder with any static file server).
2. Exercise the feature manually — there are no automated tests. Check both the "Customer" and "Internal" quote-mode tabs, light and dark theme, and (for anything touching layout/export) the print/export path via the "Print / Export project" button.
3. All app data now lives in Supabase, not `localStorage` — clearing site data / using a private window no longer gives a clean slate for a given account, since a login re-fetches everything from Postgres regardless of what's in the browser. To test "fresh account" flows, sign up a new test account instead.
4. The whole app requires the Supabase project to be reachable (real network calls to `https://bolwcxusbfsizsjtulvr.supabase.co` for both auth and data) — nothing works offline anymore, including opening a project you already created. Test accounts/projects created while testing should be cleaned up from the **Supabase dashboard → Authentication → Users** (deleting a user cascades to `profiles` → their `companies` row isn't auto-deleted by that cascade, since `companies` doesn't reference `auth.users` — delete stray `companies`/`projects` rows manually via **Table Editor** if you want a fully clean slate, or just leave them, since RLS means no other account can ever see them).

## Architecture (single IIFE, no framework)

Everything lives inside one `(function(){ "use strict"; ... })()` in the trailing `<script>` block (starts ~line 815). There's no component framework, no virtual DOM, no bundler — UI updates happen via direct DOM manipulation (`document.getElementById`, aliased as `$()`) and manual `render*()` functions that rebuild `innerHTML` for a section when state changes. Keep this style consistent rather than introducing new patterns for isolated features.

### State shape

A single in-memory `state` object (declared ~line 840) holds everything:
- `state.projects[]` → each project has `areas[]`, plus customer info and quote settings. Each area has `photo`, `placements[]` (fixtures dropped on the photo), `lightStrips[]`, `wireRuns[]`, and lighting/brightness sliders.
- `state.customFixtures[]` / `state.fixtureOverrides{}` — user-added or user-edited fixtures, layered on top of the built-in `BASE_FIXTURES` catalog (~line 820) via `allFixtures()`.
- `state.company{}` — company branding + PDF/quote appearance settings (logo, accent color, tax rate, PDF section order).
- `state.activeProfile` — the signed-in Supabase user's id. Now mostly vestigial (it predates Phase 2's real data layer) — truthy-checked in a couple of places as a loose "is someone logged in" signal, but `authUser` (see below) is the actual source of truth for that.

`state` itself still gets mutated in place and re-rendered via `renderX()` functions exactly as before Phase 2 — that part of the architecture didn't change. What changed is where mutations get *persisted*: instead of one `localStorage.setItem` of the whole object, saves now go to Supabase, scoped to just the company/project/area actually being edited (see "Auth & backend" below for why, and for the load/save functions).

### Screens

Three top-level tabs (`switchTopScreen`, ~line 1614) — Projects, Fixtures, Company — plus two fullscreen overlay modes that aren't tabs: the **Area Editor** (`#editorScreen`, `openAreaEditor`/`closeAreaEditor` ~line 1792) where photo-based design happens, and the **Crop screen** (`#cropScreen`, `openCropScreen` ~line 1844) used after any photo upload/capture.

There's also a **marketing landing page** (`#landingScreen`, top of `<body>`, `showLandingScreen()`/`hideLandingScreen()` near `setAppVisible`) shown to logged-out first-time visitors instead of the sign-in gate appearing immediately — its "Get started free"/"Sign in" buttons hide it and open `#accountModal` in the corresponding mode. A *returning* logged-in visitor never sees it: the `onAuthStateChange` listener resolves to `enterAppForUser()` before the landing page would matter, so it goes straight into the app. `leaveApp()` (fired on logout or no session) and a logged-out `closeAccountModal()`/Cancel both route back to the landing page now — it's the true "nothing to show" resting state, not the auth modal directly.

### Key subsystems (search these section-comment banners, e.g. `// ---------------- wire runs ----------------`, to navigate)

- **Canvas pan/zoom** (~line 894): desktop ctrl+scroll / pinch-to-zoom for precise fixture placement on the photo, independent of the CSS layout.
- **The design canvas (`.editor-canvas`) is always black, regardless of light/dark theme** — it's meant to simulate nighttime, so it deliberately doesn't follow `--ink`/`--surface`. This means any element placed on it (or on the always-dark print background, see the print-background note below) **cannot use theme-dependent color tokens like `var(--fog)`/`var(--line)` for text/borders and assume it'll be readable** — in light theme those resolve to dark colors meant for light surfaces, which nearly disappear against a fixed black background. This bit `.canvas-empty .btn-ghost` ("Choose photo", a real user-reported bug: text computed to `rgb(33,27,18)` on black) — `.btn-primary` elements nearby didn't have the problem because their own solid fill guarantees contrast regardless of theme, but a transparent `.btn-ghost` has nothing to fall back on. If you add new UI to the always-dark canvas (or reuse `.btn-ghost`/similar theme-token-based styles there), hardcode light colors for it rather than relying on the normal theme tokens.
- **Beam rendering** (~line 938, `buildBeamHtml`): computes the on-screen gradient/cone HTML for each placed fixture's light beam from angle, reach, brightness, and Kelvin color temp (`kelvinColor`). This same math is duplicated in Canvas 2D form for export — see `drawBeamOnCanvas` (~line 2270) — because DOM-to-canvas libraries couldn't faithfully reproduce the CSS gradients (see comment at ~line 2239). **The shape is no longer hard-edged — it now has a soft Gaussian-blurred edge (see the blur note further down) — but the underlying hard-edged wedge/circle geometry, opacity curve, and color are otherwise unchanged.** History: a "make it look more realistic" pass with *all three* of screen blend mode + blur + a small hotspot circle was tried early on and explicitly reverted per direct user feedback after seeing it live — at the time, the user preferred the hard-edged look over that softened one, and only wanted the *opacity* turned down (see the opacity note below), not blur/hotspot/blend-mode. **Blend mode was reintroduced later with confirmation (see that note), and blur has now *also* been reintroduced with confirmation** ("make the beam a bit softer on the edges" → offered a choice between a light feather and a full soft blur → user picked full soft blur, explicitly knowing it's close to the direction tried and reverted before). **The hotspot circle is the one part of the original three-part experiment that's still off the table — don't reintroduce it without confirming first.** Don't treat blur as settled/final the way you shouldn't for opacity or blend mode either — same "ask before an even bigger swing, but the current direction is confirmed-so-far" status as those.
  - **The blur is an SVG `<feGaussianBlur>` filter (`stdDeviation` = `BEAM_BLUR_STD`, in the shape's own fixed 400-unit viewBox space, 190 being the far radius), not CSS `filter:blur()` on the whole SVG element** — deliberately, to avoid the exact same "looks right at one specific rendered width, wrong at any other" trap the beam's own responsive sizing and the lit-area reveal were both already fixed for (a CSS-pixel blur radius has no way to scale itself the way an SVG filter's viewBox-relative units do automatically). This is also why the 360° pool/path-light beam changed from a plain CSS `radial-gradient` `<div>` to an SVG `<circle>` — it needed to be SVG to carry the same filter. `.beam-svg` needed `overflow:visible` added, since SVG elements clip to their viewBox by default (unlike ordinary HTML elements) and the blur spreads pixels outward past the shape's own path. The Canvas 2D export path can't use an SVG filter, so `drawBeamOnCanvas` reapplies the same `BEAM_BLUR_STD/190` ratio as a real-pixel `ctx.filter = 'blur(...)'` against that branch's own real-pixel radius — same reasoning as the hardscape base-width ratio conversion right next to it in that function, real canvas pixels standing in for viewBox units since there's no viewBox there to scale it for free.
    - **`BEAM_BLUR_STD` started at 14 and was immediately cut to 5** — a real user-reported "looks foggy now" complaint, seen right after the blur first shipped: at 14, the blur was strong enough to dissolve the cone/circle's own directional shape into an ambiguous soft blob rather than just softening its edge. This is a shared constant (used by both SVG filter instances and both canvas branches) specifically so a future retune only has to change one number. Same "confirmed too strong, not yet confirmed correct" status as `LIT_FADE_STOPS`/opacity elsewhere in this file — if a future report says it's still foggy, keep pulling this down.
  - **Blend mode specifically has since been reintroduced, deliberately and with confirmation** (unlike blur/hotspot, which have not been revisited): `.beam-svg`/`.pool` both carry `mix-blend-mode:plus-lighter` (and `drawBeamOnCanvas` sets `ctx.globalCompositeOperation='lighter'` to match, for the Canvas 2D JPG-export path) — true additive compositing, clamped at full brightness — so the beam's color adds *directly* onto the photo's own underlying brightness at each pixel instead of sitting as a flat translucent tint. An already-bright leaf highlight or pale surface gets pushed toward a strong, sometimes fully blown-out highlight; a dark gap stays comparatively dark; so the light visibly interacts with the photo's actual texture. This was an explicit user request ("make it recognize leaves/texture, not just a flat triangle on top") after being shown that true scene-aware relighting (recognizing a tree, casting real shadows from occluders) isn't feasible client-side without a depth-estimation model — blend-mode compositing was offered as the achievable middle ground, and the user chose it knowing it's the same *category* of change (blend mode) that was reverted before. **`screen` (the more conservative photo-editing blend mode) was tried first and reverted after the user reported not being able to see any difference at all against a real photo.** Root cause: at this beam's fairly high opacity (see the opacity note above), `screen`'s formula (`1-(1-a)(1-b)`) stays close to plain alpha compositing once the source is already near-opaque — there wasn't enough headroom left for backdrop luminance to visibly show through, so the "texture interaction" was real (verified via direct pixel-math comparison) but too subtle to notice by eye. `overlay`/`soft-light` were ruled out even earlier for a related reason — these scenes are usually quite dark (`photoFilterFor`'s brightness reduction simulates night), and overlay's multiply-dominant behavior on a dark backdrop would make the beam read as *weaker* exactly where it needs to look like it's adding light. Additive (`plus-lighter`/`lighter`) has no ceiling like screen does — it keeps pushing brightness up regardless of how opaque the source already reads — and is arguably the most physically correct of the three anyway (a real light adds photons; it doesn't "screen" or "overlay"). **If a future "I still don't see it" comes up, the opacity/blend-mode tension is the thing to revisit**: this beam is fairly opaque by design (see the opacity note above, a separate confirmed-but-unsettled change), and a near-opaque source layer inherently limits how much of the backdrop *any* blend mode can let through — turning opacity down somewhat (at least in the outer/dimmer part of the gradient) would let more texture interaction show, at some cost to the "vivid" look the opacity increase was for. Those two goals pull in opposite directions; don't try to solve it by escalating the blend mode again if that tension is the actual bottleneck. Like the opacity change above, this hasn't been confirmed as a keeper yet — the user hasn't seen it live and said which they prefer, so there's an annotated git tag `pre-beam-blend-mode` at the commit right before blend mode was first introduced (`screen`, since superseded by `plus-lighter`) as a safe return point back to the flat-tint version. If it needs reverting instead by hand, `mix-blend-mode` on both `.beam-svg`/`.pool` plus the `ctx.globalCompositeOperation` line in `drawBeamOnCanvas` are the only three places it touches. **Update: `plus-lighter` was confirmed liked.** The predicted "opacity/blend-mode tension" above did bite, but from a different direction than expected — not the beam's own opacity, but `photoFilterFor`'s Darkness slider being fixed (see below) to actually reach near-black. Once the ambient photo has almost no luminance left at all, *no* blend mode has any backdrop signal left to interact with, so the beam read as a flat pale shape again regardless of blend choice. Turning the beam's own opacity down (the fix predicted above) wouldn't have addressed that — see the lit-area-reveal note below for what actually did.
  - **The "flashlight" lit-area reveal** (`buildLitAreaPath`, `.photo-lit`, `litPhotoFilterFor`): a second, much-brighter copy of the area photo is stacked directly on top of the darkened one and clipped to exactly the union of every placed beam's cone/circle shape, so the areas a fixture is actually lighting up show the real photo (leaves, bark, texture) at near-full brightness, while everywhere outside a beam stays whatever the Darkness slider set — "like shining a flashlight" onto the real scene, per the user's own framing, rather than tinting a translucent shape over a near-black photo. This became necessary specifically because of the Darkness fix below: once 100% darkness reads as near-black, the beam's additive blend mode (previous note) has almost no backdrop luminance left to visibly interact with, so a purely color/blend-based beam reads as a flat pale wash again regardless of which blend mode is used — revealing the *actual* photo pixels underneath, rather than trying to synthesize the look via compositing math alone, is what actually fixes that.
    - **Present in all three beam-rendering pipelines**, each with its own `<img>`/canvas draw of the same brighter photo clipped to the same shape: the live editor (`#photoImgLit`, updated every `renderOverlays()` call), the static/print area-card thumbnail (`.photo-lit`, baked directly into `renderAreaList`'s template string — no separate refresh call needed, unlike the beam overlay, since it needs no DOM measurement at all), and the Canvas 2D JPG-export path (`captureAreaDesignImage`, via `ctx.clip(new Path2D(...))`).
    - **The clip shape is built as SVG `objectBoundingBox` fractions (0–1 per axis), not the CSS `clip-path:path(...)` function** — that distinction matters and was a real mistake caught mid-implementation: `path()` always interprets its numbers as raw pixels of the target's own box (there's no percentage/fraction equivalent), which would have reintroduced the *exact* print-reflow staleness bug that the beam's own sizing (see the separate CLAUDE.md note on that) was fixed for — a container can render at a different width in print than it did on screen, and pixel coordinates frozen at generation time don't track that. `objectBoundingBox` fractions have no such problem: the browser reapplies them against whatever the real box turns out to be, automatically, at any time — so, like the beam's own percentage sizing, this needs no `beforeprint`-style re-measurement hook (that approach was already tried once for the beam and found unreliable for real print/PDF pagination — see that note).
    - **`objectBoundingBox` scales x by the box's real width and y by its real height *independently*, which distorts a naively-uniform circle/cone into an ellipse unless compensated for.** `buildLitAreaPath` handles this by multiplying every y-going radius/offset by `aspect` (`area.photoAspect`, width/height) and leaving every x-going one alone — verified visually by placing a 360° path-light fixture and confirming its reveal renders as a true circle, not an ellipse, and by dragging a cone fixture's aim/width handles and confirming the reveal shape tracks rotation and beam-width changes exactly. `aspect` has to be passed in explicitly since fractional coordinates alone can't reveal what the real box's aspect ratio is the way pixel coordinates would.
    - **`litPhotoFilterFor()` is deliberately not tied to `area.darkness`** — fixed at `brightness(0.95)` regardless of the Darkness slider, since what a fixture's light reveals should look about the same whether the ambient scene is set dim or pitch-black, the same way a real flashlight's beam doesn't get dimmer just because the room around it got darker. Only the *shape* it's clipped to depends on the design (reach, beam width, rotation) — never its own brightness.
    - **The clip-path alone gives a hard-edged reveal — real light doesn't hit an invisible wall at its reach distance, it just gradually dims** (a real user-reported "looks kinda weird" specifically about the far edge, right after the reveal itself first shipped). Fixed by layering a `mask-image` on *top of* the existing clip-path (both apply simultaneously; the clip-path still supplies the correct angular/directional boundary — a fixture's beam width being fairly sharply defined is realistic on its own) — `buildLitFadeMaskImage` builds one `radial-gradient(ellipse Xpct% Ypct% at xPct% yPct%, white→transparent)` per placement (CSS's own percentage-of-element-box sizing, so it needs the same `aspect` compensation as `buildLitAreaPath` and is exactly as print/resize-robust), comma-joined so multiple placements' fades union via the CSS default `mask-composite: add`. The Canvas 2D export path can't share this directly (canvas has no multi-layer `mask-image` equivalent), so it's done per-placement instead: clip to that one placement's shape, `drawImage` the bright photo, then `ctx.globalCompositeOperation='destination-in'` with a matching `createRadialGradient` fade — each placement gets its own `save()`/`restore()` specifically because `destination-in` multiplies the *entire* existing canvas alpha, so doing it once per placement over a shared drawImage would have each fixture's falloff erase every other fixture's already-faded area instead of just its own.
    - **`LIT_FADE_STOPS`' peak has been tuned down twice since it first shipped, both times from real user feedback that the base still read too bright/blown-out** (`[0,1],[45,.8],[75,.25],[100,0]` → `[0,.4],[20,.65],[45,.55],[75,.15],[100,0]` → the current `[0,.15],[20,.35],[45,.3],[75,.08],[100,0]`) — the combination of a near-fully-revealed photo *and* the beam's own additive color (also strongest near the fixture) compounds fast, so it takes a much lower peak than intuition suggests to read as "soft" once both layers stack. If a future report says it's still too bright, keep pulling the whole curve down rather than assuming this settled at two rounds — there's no indication it's been confirmed correct yet, only that each prior value was confirmed *too high*.
  - **Opacity history — currently mid-experiment, not settled.** The very first version's opacity was too high, masking the photo's own detail (leaf/branch texture) instead of sitting over it translucently — a real user comparison against an actual finished-lighting photo made this obvious, so it was dropped ~30% from those original values. That lower-opacity version shipped and was confirmed correct at the time (synthetic-photo comparison, not committed, showed leaf shapes/colors staying visibly distinct under it). **It has since been bumped back up to those original (pre-dimming) values** — cone: unselected `o1=0.8`/`o2=0.39`, selected `o1=0.95`/`o2=0.5`; pool (360° path lights): unselected `o1=0.66`/`o2=0.3`, selected `o1=0.8`/`o2=0.4` — as an explicit, *tentative* user request to make beams more vivid, done specifically *without* reintroducing blur/blend-mode/hotspot (that boundary from the paragraph above still stands; only opacity moved). This has **not** been confirmed as a keeper the way the dimming was — the user asked for a "safe return point" before trying it, so there's an annotated git tag `pre-beam-opacity-boost` at the commit right before this change; `git checkout pre-beam-opacity-boost` (or `git reset --hard pre-beam-opacity-boost` on `main` if they want to discard the boost entirely) gets back to the dimmer, previously-confirmed look. Don't treat either value set as "the" correct one until the user actually says which they prefer after seeing it live — update this note once they do.
- **Fixture-type identity colors** (`FIXTURE_TYPES`/`fixtureTypeMeta`, near `kelvinColor`): each fixture has a `type` field (`accent`/`path`/`inground`/`flood`/`downlight`/`hardscape`/`other`) distinct from `kelvinColor` — `kelvinColor` is the beam's actual light-temperature color, `FIXTURE_TYPES` is a fixed identity color per fixture *type* used purely so a placement dot, its row in the materials list, and the legend all agree on "which color means what," regardless of what color that fixture actually emits. Colors are set inline per-instance (not hardcoded in CSS) at every place a fixture shows up: the canvas marker-dot (`renderOverlays`), the static/print place-dot (`buildStaticOverlaysHtml`), the canvas-export dot (`drawDotAndLabelOnCanvas`), the materials/quote table rows and fixture-picker/fixture-library lists (`quoteItemNameCell`, reused across `renderProjectQuote`/`renderSheetList`/`renderFixtureMgmtList`), and two legends (`usedFixtureTypes`+`buildTypeLegendHtml`) — a floating one over the design canvas (`#editorLegend`, scoped to the current area's placements) and one in the project detail "Areas" section (`#areaTypeLegend`, scoped to the whole project, which also prints since that section isn't print-only). Both legends only list types actually in use, not the full fixed set, to avoid clutter on a design that only uses one or two types. **In print, `.place-dot`'s CSS forces `background:#fff` for contrast against any photo — the inline per-type `border-color` still wins over that class rule** (inline beats class regardless of media query), so it prints as "white fill, type-colored ring," same identity color as on-screen; don't try to also force border-color in that print rule, it would silently defeat the whole feature there. Custom fixtures and base-fixture overrides created before this feature don't have a `type` — `fixtureTypeMeta` falls back to `other` (grey), consistent with how other schema-less-JSONB fixture fields degrade elsewhere in this file.
- **Hardscape fixtures** (`f10` in `BASE_FIXTURES`, `type:'hardscape'`): a 6" linear bar fixture for steps/walls/paver joints, added as a regular catalog `cat:'fixture'` entry with its own identity color and specs matching a real hardscape light's subtle output (wide-ish `beam:100`, low `lumens:90`/`watt:2`). Unlike every other fixture type, it gets two deliberately different visuals, per direct user feedback that the initial version (reusing the standard point-source rendering as-is) didn't read as a linear source:
  - **Marker is a rotated bar, not the round dot every other fixture uses** — `.marker-dot.is-bar`/`.place-dot.is-bar` (smaller width/height + less rounding than the base class) plus an inline `transform:translate(-50%,-50%) rotate(${p.rotation}deg)` applied only for `f.type==='hardscape'`, in all three render paths (`renderOverlays`, `buildStaticOverlaysHtml`, `drawDotAndLabelOnCanvas`). The bar's un-rotated default orientation (wider than tall) is already perpendicular to "up" (`p.rotation===0`), so `rotate(p.rotation)` alone keeps it perpendicular to wherever the beam is aimed — no extra +90° offset needed. Note the `.just-placed` pop animation's own `transform` keyframes momentarily override this inline rotation for its ~0.5s duration (CSS animations win over inline styles in the cascade); the bar snaps back to its correct rotation once the animation ends and the class is gone on the next render. Harmless, not worth fixing.
  - **Beam has a flat trapezoid base instead of converging to a point** — a real 6"+ LED bar doesn't emit from a single point the way a spot fixture's lens does. `HARDSCAPE_BASE` (=22, a half-width in the same fixed 400-unit space `buildBeamHtml`'s far radius of 190 already uses) defines two extra path points at ±90° from center, so the SVG path becomes `base-corner → far-arc-start → arc → far-arc-end → other-base-corner → close` instead of `center → far-arc-start → arc → far-arc-end → close`. `drawBeamOnCanvas`'s canvas-export equivalent has to re-derive the same 22/190 ratio by hand against the real pixel radius `R`, since canvas drawing has no viewBox to scale the fixed-unit-space math for free the way the SVG version does.
- **Wire runs & LED strips** (~lines 1017, 1039): freehand paths drawn on the photo, stored as point arrays, rendered as SVG overlays live and re-drawn onto canvas for export.
- **Drag/placement handlers** (~line 1192, `makeDraggable`; ~line 1216, `attachPlacementHandlers`): pointer-event-based dragging for moving fixtures, aiming beams (ring handle), and widening beams (square handle).
- **Undo/redo** (section banner `// ---------------- undo/redo (area editor) ----------------`, near the other module-level editor state): snapshot-based, not a command pattern — `pushUndoSnapshot()` JSON-stringifies the current area's `placements`/`wireRuns`/`lightStrips`/`accessoryQty`/`darkness`/`beamBrightness` onto `undoStack` (capped at `UNDO_LIMIT`, 50) *before* a mutation happens, and `undoDesign()`/`redoDesign()` pop/push between `undoStack` and `redoStack`, restoring via `applySnapshot()`. Scoped to whichever area is currently open — both stacks are reset in `openAreaEditor()`, so undo history never carries across areas or projects. A fresh action (anything that calls `pushUndoSnapshot()`) always clears `redoStack`, matching standard undo/redo semantics — once you make a new change, the old "future" is gone. JSON-stringifying is deliberate: it makes each stack entry a real independent copy, so later mutating the live area object can never retroactively corrupt a snapshot already on the stack (a plain object reference would not have this guarantee).
  - **Every mutation site needs its own `pushUndoSnapshot()` call — there's no central interceptor.** Since this isn't a proxy/observer over `state`, adding a new way to mutate an area's design (a new tool, a new modal, a new stepper) means remembering to add the call yourself at that exact call site, ideally as the first line after validating the mutation will actually happen. Current call sites: placing a fixture (`handleCanvasClick`), removing/duplicating one (`infoRemove`/`duplicatePlacement`), dragging a fixture/beam-aim/beam-width handle (`makeDraggable`'s `move()`, only once the 4px drag threshold is crossed — not on every `pointermove`, and not on a plain click that never becomes a drag), saving or deleting a wire run or LED strip (`saveWireModal`/`deleteWireRun`/`saveStripModal`/`deleteLightStrip`), accessory qty +/- (the `[data-inc]`/`[data-dec]` handlers in `renderSheetList`), and "Clear design". The four range sliders that mutate area/placement state continuously while dragged (`ctrlDarkness`, `ctrlBeamBrightness`, `infoKelvin`, `infoBrightness`) snapshot on `pointerdown` rather than on every `input` event, so a whole drag of the slider is one undo step instead of dozens — the same one-snapshot-per-gesture idea as the drag handles, just triggered by `pointerdown` instead of a distance threshold since there's no separate "click vs. drag" distinction to make for a slider.
  - **`.edit-panel` (the shared base class for every bottom-sheet modal — customer, fixture form, area name, distributor, and the per-fixture info sheet with `infoKelvin`/`infoBrightness`) needs `user-select:none`, or dragging a range slider inside one only works some of the time — a real user-reported "sliders rarely work" bug.** Root cause, confirmed directly (not just suspected): a drag gesture that doesn't land in the exact pixel-perfect hit-region of the thumb falls through to the browser's native text-selection drag instead, since nothing was suppressing it — `window.getSelection().toString()` after a failed drag returned a real non-empty fragment of the panel's own hint text, proving the browser had claimed the gesture as a text selection instead of passing it to the slider. This is the *same* root cause as the documented wire-run/photo-selection bug on the design canvas (`user-select:none` + `preventDefault()` needed together there) — just never applied to this other, unrelated place a drag can happen. The event-handler *logic* itself was verified correct independently (setting `.value` and dispatching a synthetic `input` event always worked) — the bug was purely about the gesture never reaching the slider at all, not about what happens once it does. `user-select:none` doesn't affect an `<input>`'s own internal text editing/selection (that's standard browser behavior, unaffected by an ancestor's `user-select`), so this doesn't stop typing in e.g. the customer name field, which shares the same `.edit-panel` class — verified directly. Deliberately not `touch-action:none` on the same rule — that would also block touch-scrolling the panel's own content on mobile (`.edit-panel` has `overflow-y:auto;max-height:90vh`), which `user-select:none` doesn't touch.
  - **Ctrl+Z/Cmd+Z undoes, Ctrl+Shift+Z or Ctrl+Y redoes** — a single `keydown` listener on `document`, gated on the editor screen being open (`!$('editorScreen').hidden`) and on focus not currently being in a text-like field (`<textarea>`, `contenteditable`, or an `<input>` whose `type` isn't `range`/`checkbox`/`radio`) so it doesn't fight a browser text-undo the user is actually trying to do in, say, the customer-name field elsewhere in the app. Range sliders are deliberately exempted from that text-field check — they have no native undo of their own, so Ctrl+Z should still reach the app's undo while a slider has focus.
  - **`#btnUndo`/`#btnRedo` disable via the plain `disabled` attribute, not `hidden`** — unlike the fixture-type legend/toolbar/banner elsewhere in this file, there's no `[hidden]`-vs-author-`display` gotcha here since `:disabled` is a real interactive-element state the browser itself enforces, not a display toggle fighting a class rule.
- **Drawing a wire run or LED strip (drag across the photo) needs BOTH a JS `preventDefault()` on the pointerdown/pointermove handlers AND `user-select:none` on `.editor-canvas` — one alone isn't enough.** A real user-reported bug: the photo would flash blue mid-drag, like a text/image-selection highlight. Root cause: the browser's native "drag across the page = select text/images" gesture was never suppressed. `preventDefault()` on `#canvasPhoto`'s pointerdown/pointermove (added for the wire/strip/pan/pinch drags alike) covers drags that start on the photo itself, but the photo doesn't always fill `.editor-canvas` (aspect-ratio letterboxing can leave black margin on the sides) — a drag starting in that margin never reaches a handler that calls `preventDefault()`, so it still triggers a selection, which still visually reads as "the canvas flashed blue" since the margin is the same black as the photo backdrop. `user-select:none` on `.editor-canvas` (not just `#canvasPhoto`) closes that gap. Verified by driving real OS-level mouse drags (not synthetic dispatched events, which don't reliably trigger the browser's native selection gesture the same way) both on the photo and in the letterboxed margin, and checking `window.getSelection().rangeCount` before/after each — confirmed 0 in both cases after the fix, 1 (a real non-collapsed selection) in each case before it.
- **Any element toggled via the `hidden` DOM property/attribute must NOT also get its `display` set unconditionally by a plain class selector — that class rule (an author style) silently wins over the browser's built-in `[hidden]{display:none}` default (a user-agent style), regardless of the `hidden` attribute actually being set.** This is why `.edit-sheet`, `.editor-screen`, and `.crop-screen` each have a matching `.foo[hidden]{display:none;}` rule right next to their base rule — every one of them sets `display` unconditionally (`flex`) and needs the explicit override to make `hidden` actually work. **`.placement-banner`, `.canvas-toolbar`, and `.type-legend` were missing this same override** — a real user-reported bug (hitting "Done" after placing a fixture didn't make the banner go away) traced back to exactly this: `banner.hidden = true` was being set correctly, `updatePlacementBanner()`'s logic was correct, but the element's actual computed `display` stayed `flex` regardless, so the banner (with its now-stale "N placed" text) just sat there. Verified directly via `getComputedStyle(el).display` before/after the fix (not just visually) — was `"flex"` despite `el.hidden===true` before, `"none"` after, for all three elements. **If you add a new absolutely-positioned overlay to the editor canvas (or anywhere else) that sets its own `display` and gets toggled via `.hidden`, it needs this same `[hidden]` override — the bug is invisible in code review since `updatePlacementBanner()`/equivalent logic looks completely correct on its own; it only shows up as computed style.**
- **Quote math** (~line 1483): `computeAreaLineItems`/`computeProjectLineItems` roll up placements + strips + accessories into priced line items; toggled between "Customer" (sell price) and "Internal" (cost) modes.
- **`#projQuoteTable`'s subtotal/discount/tax/total block (`#projQuoteTfoot`) is a plain `<tbody>`, not a `<tfoot>` — this is deliberate, not an oversight.** Browsers automatically repeat `<thead>`/`<tfoot>` on *every* printed page a table spans across; for a real `<tfoot>` holding the totals, that meant a long item list printed the subtotal/discount/tax/total rows once per page instead of once at the true end — a real user-reported bug that looked like two separate partial quotes. `<tbody>` never gets that auto-repeat treatment, so switching the tag fixes it (both the "Customer" and "Internal"/cost-mode footers in `renderProjectQuote` populate the same `#projQuoteTfoot` element regardless) while leaving `#projQuoteThead` as a real `<thead>` — repeating the *column headers* on each page is what you actually want for a multi-page table. Don't "fix" `#projQuoteTfoot` back to a semantic `<tfoot>` without re-solving this.
- **Fixture library + Excel import** (~lines 1885–2119): SheetJS (`xlsx.full.min.js`, CDN) reads an uploaded spreadsheet; `findFixtureHeaderRow`/`parseFixtureRows` locate and parse fixture rows against a downloadable template (`downloadFixtureTemplate`).
  - **The template is a real `.xlsx` binary embedded as a base64 string (`FIXTURE_TEMPLATE_B64`), not generated on the fly** — there's no server and no xlsx-writing library loaded (SheetJS is only used for *reading* an import), so the actual approach is: hand-build/edit the real `.xlsx` as a zip of OOXML parts (this file has no sharedStrings.xml — cells use inline `t="inlineStr"`, so there's no separate strings table to keep in sync when editing rows), then base64-encode the whole file and paste it in as the JS constant. **If you ever need to change the template's columns/wording again, don't hand-edit the base64 — decode it, edit `xl/worksheets/sheet1.xml` (and `<cols>`/`<dimension>`/`<mergeCells>` refs if the column *count* changes), re-zip, re-encode, and verify by feeding the result back through `XLSX.read()` (the exact library the app uses for real imports) before committing.** column C ("Fixture Type") was added this way when fixture-type color-coding shipped — `parseFixtureRows`'s column indices (`row[2]` onward) and this template's columns must stay in lockstep; changing one without the other silently misreads every column after the change point.
- **Removing a built-in fixture from the library doesn't delete anything — it can't, `BASE_FIXTURES` is a hardcoded array, not database rows.** It sets `hidden:true` on that id's entry in `state.fixtureOverrides` (the exact same table/mechanism already used for editing a built-in's fields — a "removed" fixture is just an override with `hidden:true`, possibly alongside other customized fields). `allFixtures()` filters these out; `findFixture(id)` deliberately does *not* apply that filter, so a fixture already placed on an existing design keeps resolving correctly (via `BASE_FIXTURES.find` + override) instead of silently breaking that area's rendering/pricing once hidden. Restorable from "Removed from your library" at the bottom of each category tab (`renderFixtureMgmtList`) — `restoreFixture()` deletes just the `hidden` key, keeping any other customization on that override, and only deletes the whole override row if `hidden` was the only thing in it. Custom fixtures (`state.customFixtures`) are unaffected by any of this — those are real rows, and their "Delete" button (label switches based on `f.custom`) still does a real, permanent `custom_fixtures` delete with no restore path, exactly as before.
- **PDF / export** (~line 2154): "PDF export" is actually the browser's native `window.print()` against a print stylesheet (`applyQuoteAppearance`, `applySectionOrder` reorder printed sections per company settings). A separate path, `exportAreaImagesOnly`/`captureAreaDesignImage` (~line 2354), renders a design (photo + beams + wires + strips) onto an offscreen `<canvas>` at higher resolution to produce a flat JPG when the user wants images without the quote table.
  - **The printed/PDF area photo is deliberately *not* the same fixed-height `object-fit:cover` thumbnail used on-screen in the projects list.** On screen, `.area-card-photo` is a short fixed-height crop (150–260px depending on breakpoint) — fine for a scrolling list of small cards, but it crops off whatever doesn't fit, which can (and did — a real user-reported bug) hide part of a design, like a beam or fixture placed lower in the photo. The `@media print` block overrides this to `height:auto` + `object-fit:contain` so the printed quote — the actual customer-facing deliverable — always shows the complete, uncropped photo at its real aspect ratio. If you ever need to change how tall the print photo renders, override `height`/`object-fit` in `@media print`, not the base `.area-card-photo` rule — changing the base rule affects the on-screen thumbnail too.
  - **The static/print beam overlay (`buildStaticOverlaysHtml`) sizes its beam as a CSS percentage of width (`aspect-ratio:1` + `width:N%`, via `buildBeamHtml`'s `responsive=true` path) instead of the fixed pixel `width`/`height` the live editor uses (`renderOverlays`, `responsive` omitted/false) — this is a deliberate, load-bearing difference, not an inconsistency to "clean up."** A real user-reported bug: a beam that reached well up into a tree's canopy in the live editor showed only a short way up it in the exported PDF/print. Two fixes were tried before landing on this one — both worth knowing about so they aren't retried: (1) deriving `rect.height` from `area.photoAspect` instead of the on-screen cropped box's real height — didn't help, because `clampR`'s formula barely depends on `rect.height` at all in practice (only as a rarely-binding upper-clamp ceiling); the real dependency was on `rect.width`. (2) Re-running the pixel-based generation on the `beforeprint` event (the browser guarantees print media styles are already applied by the time it fires, unlike measuring synchronously before `window.print()`) — this *did* work in a synthetic test (resizing the viewport and dispatching a fake `beforeprint`), but the user reported the PDF was still wrong, meaning real print/PDF pagination doesn't reliably reflect back to `getBoundingClientRect()` the way an on-screen resize does — there's no JS hook that reliably observes the print layout's actual width. **The fix that actually worked sidesteps measuring entirely**: the beam sizes itself as `width:${R*2/rect.width*100}%` (width cancels out of the formula algebraically, so the percentage is independent of whatever `rect.width` was at generation time) with `aspect-ratio:1;height:auto` to stay square regardless of the container's own aspect ratio, using a fixed reference rect (`{width:380, height:380/area.photoAspect}`) purely to reproduce the existing reach-scaling and min/max-clamp formula — its absolute size doesn't matter since the percentage divides it back out. The browser's own layout engine then keeps it correctly sized at *any* future width — on-screen, print, resized, anything — with no JS involved at all, which is what makes it actually reliable where re-measuring wasn't. This needed a supporting CSS change too: `.area-card-photo .overlays .placement{width:100%;height:100%;}` — percentage sizing on the beam only resolves against a containing block (`.placement`) that itself has a *definite* size, and `.placement` is normally unsized (auto/shrink-to-fit), which the live editor's pixel-based children don't care about but a percentage-based child does; this rule is scoped to `.area-card-photo` specifically so it can't reach the live editor's own `#overlays .placement`, which must keep pixel-based sizing for its drag-handle math (`hx`/`hy`/`wx`/`wy`, used by `renderOverlays`/`updatePlacementBeam`, both of which correctly omit `responsive`). Verified by resizing the viewport with *no* JS re-render call at all and confirming the beam's computed pixel size tracked the container width proportionally (and stayed exactly square) purely via CSS. If you ever add another static (non-live-editor) rendering of a beam, give it this same percentage-based treatment from the start — a fixed-pixel size frozen at generation time is the mistake that started all this, and re-measuring-at-the-right-moment is a trap that looks like a fix but isn't reliable for print specifically.
  - **`html`, `body`, and `.app` all carry their own explicit background color, and print needs to override all three — not just one or two of them.** `html,body{background:var(--ink-2)}` is declared *twice* (the base rule, and again inside `@media (min-width:860px)`), and `.app{background:var(--ink)}` separately. In light theme both `--ink` (`#F4F1EA`) and `--ink-2` (`#E7E2D6`) are cream/tan tones, not white. **First attempt at this fix only overrode `body` and `.app`, and missed `html`** — since `html` is the outermost element, its leftover tan background still bled through as a "weird tan" block below the quote content, which is exactly what the user saw even after that first fix shipped; verified by reproducing it (checking computed `background-color` on all three elements with only `body`/`.app` overridden showed `html` still resolving to `--ink-2`'s tan, `rgb(231,226,214)`) before fixing it for real with `html,body{background:var(--pdf-bg-color,#fff);}` plus `.app`'s own override. If you ever touch this again: grep for every `background:var(--ink` and `background:var(--ink-2` declaration first, not just the ones that seem obviously relevant — there were three, in three different places, and it was easy to fix two and still leave the bug in place.
  - **Quote footer**: `state.company.footerText` (free text, `companies.footer_text` column) renders into `#printFooter` via `renderCompanyFooterForPrint()` (called from `renderCompanyPreview()`, same pattern as the header). It's deliberately *not* part of the reorderable `sectionOrder` list — a footer is always last by definition — so it isn't marked with a `data-section` attribute; instead `#printFooter` has a hardcoded `order:100` (all reorderable sections are 0–4), guaranteeing it's always last regardless of section order. Line breaks in the textarea are preserved via a `\n` → `<br>` replace after `escapeHtml()`.

### Auth & backend (Supabase)

- **Client init** (~line 894): `sb = window.supabase.createClient(SUPABASE_URL, SUPABASE_ANON_KEY)`, loaded via the `@supabase/supabase-js@2` CDN script tag in `<head>`. The anon key is intentionally public — it's safe to be in client-side code because row-level security (RLS) is what actually restricts access, not the key itself. Never put the `service_role` key in this file.
- **Schema**: see `supabase/schema.sql` — the actual source of truth for the live schema (`companies`, `profiles`, `projects`, `areas`, `custom_fixtures`, `fixture_overrides`, all RLS policies, the `handle_new_user` trigger), kept manually in sync since there's no migrations CLI wired up. If you change the schema, update `supabase/schema.sql` in the same session (and run the SQL yourself via the Supabase SQL Editor — there's no tool/CLI access to the database from this environment).
- RLS is scoped through a `security definer` helper function `current_company_id()`. **Do not** write a `profiles` RLS policy as a raw subquery against `profiles` itself (e.g. `company_id in (select company_id from profiles where id = auth.uid())`); that causes Postgres error 42P17 "infinite recursion detected in policy," which is exactly what happened the first time this was built. Always route self-referencing lookups through the `security definer` function instead.
- **Signup auto-creates a tenant**: a Postgres trigger (`handle_new_user`, defined in Supabase) fires on every `auth.users` insert, reading `company_name`/`full_name`/`access_code` out of the signup call's `options.data` and creating one new `companies` row + one `profiles` row (`role: 'owner'`) per signup — but only if `access_code` matches the hardcoded gate value (see the access-code note above); otherwise it raises and the whole signup fails. There is currently no invite flow for adding a second person to an existing company — every signup is a brand-new tenant.
- **App-side auth flow** (~lines 2690–2740): `sb.auth.onAuthStateChange` (subscribed once in `init()`) is the single source of truth for entering/leaving the app — `enterAppForUser()` on a session, `leaveApp()` on none. Session persistence (surviving a page reload) is handled entirely by supabase-js itself via its own `localStorage` key; nothing in this app's code re-implements that. The `#accountModal` element is dual-purpose: it's the mandatory sign-in/sign-up gate when logged out (`.app` is hidden via the `auth-hidden` CSS class until a session exists — see `setAppVisible`), and becomes an account-info/log-out panel when logged in — `openAccountModal()` branches on whether `authUser` is set.

**Data sync** (~lines 2536–2635, section banner `// ---------------- data sync (Supabase) ----------------`) is where projects/areas/company/fixtures actually move between `state` and Postgres. The load side and the save side are deliberately asymmetric:

- **Loading is eager**: `loadCompanyDataFromDb(companyId)`, called once from `enterAppForUser`, fetches the company row, *all* projects, *all* areas (via RLS alone — no explicit filter needed, since the `areas` RLS policy already scopes it), and the whole fixture library, then populates `state` in one shot — mirroring exactly what the old localStorage blob used to hand back. This is intentionally not optimized (e.g. not lazy-loading areas per-project) — Phase 3 (moving photos out of the JSON) is where that would actually start to matter; doing it now would be solving a Phase 3 problem inside Phase 2.
- **Saving is scoped, not eager.** This is the important part, and it's not just a performance choice — see the migration-progress note above about why a single whole-account blob write isn't safe once more than one person can be editing a company's data at once. `flushCurrentEdits()` only ever writes the company row plus whichever project/area `currentProject()`/`currentArea()` currently point to — never the rest of `state.projects`. It runs on a 5s `setInterval`, on `beforeunload`/`pagehide`, and is explicitly called before anything that would change what "current" means: `closeAreaEditor()`, and `openProjectDetail()` (flushing the *previous* project before switching `state.currentProjectId`). **If you add a new screen or navigation path that changes `currentProjectId`/`currentAreaId`, add a `flushCurrentEdits()` call before that reassignment**, the same way `openProjectDetail` does — otherwise pending edits to whatever was open before can be silently dropped once "current" points elsewhere.
- **Discrete create/delete/explicit-save actions bypass the scoped-save mechanism entirely and write immediately**: new project (`customerSave`), new area (`areaNameCreate`), project delete, area delete, and fixture add/edit/delete/import all do their own direct `sb.from(...).insert/update/delete(...)` call right at the point of the user's click — these don't wait for the tick since they're one-off actions, not continuous edits like dragging a fixture or typing in a field.
- **Row \<-> `state` shape mapping** (`companyToRow`/`rowToCompany`, `projectToRow`/`rowToProject`, `areaToRow`/`rowToArea`) converts between Postgres's snake_case columns and the app's existing camelCase in-memory shape. If you add a field to `state.company`/a project/an area, it needs a matching column in `supabase/schema.sql` *and* both directions of the corresponding mapper function, or it'll silently fail to persist.

**Photo/logo storage** (Phase 3, ~lines 2645–2668): `uploadAreaPhoto(area, dataUrl)` and `uploadCompanyLogo(dataUrl, contentType)` both go through a shared `uploadToPhotosBucket(path, dataUrl, contentType)` — convert the data: URL (produced by the crop canvas) to a `Blob`, upload to the public `photos` bucket at a path starting with `{companyId}/...` (area photos: `{companyId}/areas/{areaId}.jpg`; logo: `{companyId}/logo.{ext}`), and return a cache-busted public URL (`?v=<timestamp>` appended — needed because the path is stable and uploads use `upsert:true`, so without a cache-buster a re-cropped photo could keep showing the old cached image at the same URL). `area.photo`/`state.company.logo` get set to that returned URL, same as they'd previously have been set to a raw data: URL — nothing downstream (rendering, PDF export) needed to change, since an `<img src>` doesn't care whether it's a data: URL or an https:// URL.
- **Any `<img>` that gets drawn onto a `<canvas>` and then read back out (`toDataURL`) needs `img.crossOrigin = 'anonymous'` set before `img.src`, full stop, whenever that image might be a Storage-hosted `https://` URL rather than a `data:` URL.** Two separate places load `area.photo` into a fresh `Image()` for exactly this purpose — `openCropScreen` (Adjust crop) and `captureAreaDesignImage` (the "export design photos as JPG only" flow) — and **both** need the attribute independently; fixing one does not fix the other, since they're unrelated `<img>` elements. `openCropScreen`'s missing `crossOrigin` was caught during Phase 3 testing; `captureAreaDesignImage`'s was a second, separate instance of the identical bug, found later because a user reported "the JPG export button does nothing" (the tainted-canvas exception thrown inside `img.onload` was uncaught, so the `Promise` in `captureAreaDesignImage` just hung forever instead of resolving or rejecting — that's now also caught with a try/catch that resolves `null` on failure instead of hanging). If a third place ever loads a Storage photo into a canvas, it needs this too — it will not fail loudly without it.
- Area/project delete also removes the associated Storage object(s) (`sb.storage.from('photos').remove([...])`, fire-and-forget) so deleted photos don't pile up as orphaned files — see the project/area delete handlers in `renderProjectList`/`renderAreaList`.

### Editing conventions specific to this file

- New UI elements are added as plain HTML in the relevant screen's markup block (search the `<!-- ===== SECTION ===== -->` banner comments in the body, ~lines 388–814), then wired up with `addEventListener` calls inside `init()` (~line 2741, the largest function in the file).
- Fixture/accessory/strip categories are distinguished by `cat: 'fixture' | 'accessory' | 'strip'` throughout — filtering and rendering logic branches on this field repeatedly (sheet lists, quote line items, import parsing).
- Money values are always formatted through the `money()` helper (~line 873); don't hand-roll currency formatting.
- Adding a new field to a project/area/company/fixture now touches three places, not one: a column in `supabase/schema.sql` (run via SQL Editor), both directions of the relevant `rowTo*`/`*ToRow` mapper function, and a sensible default read (`x.newField || default`) at call sites — existing rows in the database won't have the new column backfilled, and there's no migration runner to do it for you.
- **Always wrap user-entered text in `escapeHtml()` before interpolating it into an `innerHTML` template string** — customer names, area names, and fixture name/desc are all typed by users and end up in `<div>...=`${...}`...</div>`-style templates throughout the render functions. A real stored-XSS gap here (customer/area/fixture name rendered unescaped in several places — the projects list, area cards, fixture sheet/library lists, both quote tables) was found and fixed in the same session that added the CDN integrity hashes below; don't reintroduce it in new render code. Values set via `.textContent` or an `<input>`'s `.value` don't need this — only raw `innerHTML` string-building does.
- **The two CDN `<script>` tags in `<head>` (SheetJS, `@supabase/supabase-js`) are pinned to an exact version with a `sha384` `integrity` hash and `crossorigin="anonymous"`.** If you ever bump either version, you must recompute the hash for the new file (e.g. `curl -s <url> | openssl dgst -sha384 -binary | openssl base64 -A`) and update both the `src` URL and `integrity` together — an unpinned version range (like the old `@supabase/supabase-js@2`) can't have a stable SRI hash at all, since the served file changes over time.
